# 功能梳理

## 何时使用本技能

- 改动前想知道「动这里会牵连哪些地方」
- 排障时想定位「这条链路哪一环出了问题」
- 要给别人（或未来的自己）讲清一个功能怎么实现的

范围是**单条功能链路**，不是整个仓库（整仓上手用 `project-onboarding`）。

## 核心方法：抓两个端点，再连中间

功能链路 = 一个**入口**到一个**出口**之间发生的所有事。先钉死两端，再往中间填。

```
入口候选：路由 / 按钮的 onClick / 命令 / 定时任务 / 消息消费者 / API handler
出口候选：数据库写入 / HTTP 响应 / 文件产出 / 发出的消息 / 屏幕渲染
```

## 执行流程

### 1. 锁定入口

用用户能描述的现象反查入口：

- 界面功能 → 搜按钮文案、搜路由路径
- 接口 → 搜 URL path、搜 handler 名
- 后台任务 → 搜任务名、cron 配置、消费的 topic

找到入口函数，记下 `file:line`。

### 2. 顺链路走，边走边记

从入口开始，跟着调用往下走，每一跳记一行：

```
[入口]  routes/order.py:42        POST /order/submit
  → services/order.py:88         validate_and_create()
  → repository/order.py:31       insert()  ← 数据库写入
  → mq/publisher.py:12           publish("order.created")  ← 副作用
[出口]  返回 201 + order_id
```

跟踪技巧：

- 用「查找引用 / 跳转定义」而不是猜
- 遇到接口/抽象类，找到**实际注入的实现**再继续
- 异步边界（消息队列、事件、定时）要标出来——链路在这里「断开」再从消费端接上
- 条件分支只跟与当前功能相关的那条，其它标注「另有分支处理 X」

### 3. 标出数据的形态变化

链路上数据长什么样、在哪被改：

- 入参结构 → 校验后 → 存储结构 → 响应结构
- 哪里做了转换、默认值填充、脱敏、序列化
- 哪些字段是外部可控的（安全审查关注点，见 `security-audit`）

### 4. 列影响面

基于链路，回答「改动会影响谁」：

- **上游**：谁会调用这个入口（直接调用方 + 间接）
- **下游**：这条链路写的数据/发的消息，谁在消费
- **共享**：链路上用到的公共函数/表/配置，别处是否也在用
- **契约**：改了出参结构 / 消息格式，哪些消费方要同步改

## 产出模板

```
# 功能：<一句话>

## 链路
入口 <file:line> → ... → 出口 <file:line>
（逐跳列出，标注 DB 写入 / 网络调用 / 消息 / 异步边界）

## 数据流
入参 <结构> → <关键转换点> → 存储 <表/字段> → 出参 <结构>

## 影响面
- 上游调用方：...
- 下游消费方：...
- 共享依赖：...
- 契约变更风险：...

## 改动落点建议
要实现 <目标>，应改动 <位置>，因为 ...
需要同步注意 ...
```

## 排障用法

当目的是定位 bug：在链路每一跳问「数据到这里还对吗」，用二分法缩小——在链路中点加日志/断点，看数据在中点前还对不对，快速把问题夹逼到某一跳。定位到后交给 `systematic-debugging` 深入。

## 反面案例

| 不要这样 | 要这样 |
|---|---|
| 靠猜「大概在这个文件」 | 用查找引用逐跳确认 |
| 跟到接口就停 | 找到实际实现继续跟 |
| 忽略消息/事件的异步跳转 | 标出异步边界并从消费端接上 |
| 只说「改这个函数」 | 同时给出上下游影响面 |
| 把整个仓库都讲一遍 | 只聚焦这一条功能链路 |
