# 视觉验证测试

## 何时使用本技能

- 改完任何界面，要确认真实渲染效果
- 验证响应式、暗色模式、多状态（空/加载/错误/满）
- 改动前后像素级对比、回归检查

## 铁律：看真实渲染，不靠「代码看着对」

界面正确与否，只有**真实渲染出来的样子**说了算。读代码推断「应该没问题」不算验证。必须让页面在真实浏览器里跑起来、截图、亲眼看。

## 执行流程

### 1. 让页面真正跑起来

- 用项目既有方式启动（dev server / Storybook / 预览命令）
- 用浏览器自动化（Playwright / Puppeteer / Claude-in-Chrome 等本项目可用的方案）打开目标页面
- 等到网络与动画稳定再截图，别截到加载中途

### 2. 覆盖矩阵，而不是只看一张

一个界面改动，至少覆盖这几个维度的组合：

| 维度 | 取值 |
|---|---|
| 视口 | 移动端(375) / 平板(768) / 桌面(1440) |
| 主题 | 亮色 / 暗色 |
| 状态 | 正常 / 空数据 / 加载中 / 错误 / 超长内容 |

不必全笛卡尔积，但**改动直接影响的维度必须都截**。比如改了响应式布局，三个视口都要看；加了暗色支持，两个主题都要看。

### 3. 改动前后对比

回归验证的关键是对比：

- 改动**前**先对基线截图（或用已有基线）
- 改动**后**同参数再截
- 逐张比对：期望变化的地方变了吗？**不该变的地方有没有被误伤**？

误伤（改 A 弄坏了 B）是回归的主要来源，对比就是为了抓它。

### 4. 不只看「长得对」

截图时同时检查：

- **控制台**：有没有报错、警告、404、CSP 拦截
- **布局健康**：有没有溢出、错位、横向滚动条、文字被截断、元素重叠
- **交互态**：hover / focus / active / disabled 的样子对不对
- **可访问性**：焦点框可见吗、对比度够吗

### 5. 转成明确判定

每张截图给出**明确结论**，不要含糊：

```
✓ 桌面亮色：筛选栏对齐正确，与设计一致
✓ 移动 375：折叠为下拉，无横向滚动
✗ 暗色：筛选栏文字 #333 在深色背景上几乎不可见 —— 需改用主题令牌
✗ 空数据：空态占位缺失，显示为一片空白
```

有 ✗ 就回去改，改完重新截同一组对比，直到全 ✓。

## 与其它技能配合

- 界面实现本身用 `frontend-development`
- 逻辑层面的回归用单元/集成测试（`test-driven-development`）
- 本技能专管「肉眼可见的正确性」

## 反面案例

| 不要这样 | 要这样 |
|---|---|
| 「代码没问题，应该 OK」 | 截真实渲染图亲眼确认 |
| 只截桌面亮色一张 | 覆盖受影响的视口/主题/状态 |
| 改完只看目标区域 | 对比不该变的区域有没有被误伤 |
| 截图但不看控制台 | 同时检查报错、溢出、横向滚动 |
| 「看起来差不多」 | 每张给出 ✓/✗ 明确判定 |
| 发现问题改完不复验 | 改完重新截同组图直到全 ✓ |
