# 代码漏洞审核

## 何时使用本技能

- 明确的安全审查请求
- 改动涉及：认证/授权、用户输入、文件/路径、外部请求、加解密、密钥、序列化、SQL/命令
- 上线前的安全过一遍

本技能只做**防御性审查**：找问题、给修复。不产出可直接滥用的攻击代码。

## 审查方法：跟着不可信数据走

漏洞几乎都发生在**不可信数据**（用户输入、外部接口返回、文件内容、URL 参数）到达**危险操作**（执行、查询、读写文件、发请求、反序列化）的路径上。

```
不可信来源  →  [是否校验/转义/参数化?]  →  危险汇聚点
```

审查就是：找出所有危险汇聚点，逆着数据流回溯，看中间有没有做防护。

## 逐类排查清单

### 注入
- **SQL**：有没有字符串拼接 SQL？→ 必须参数化查询 / ORM 绑定
- **命令**：有没有把输入拼进 shell / `os.system` / `subprocess(shell=True)`？→ 用参数列表、禁 shell
- **模板/表达式**：用户输入进模板引擎、`eval`、`exec`？→ 禁用或严格白名单

### 认证与会话
- 密码是否加盐哈希（bcrypt/argon2），而非明文/MD5
- 会话 token 是否足够随机、有过期、登出即失效
- 敏感操作是否校验当前身份，而非信任前端传来的 user_id

### 越权（授权）
- 每个能拿到别人数据的接口，是否校验「这条数据属于当前用户」（IDOR）
- 越权分水平（改 id 看别人的）和垂直（普通用户调管理员接口）——两者都查
- 前端隐藏按钮 ≠ 后端有校验；后端必须独立鉴权

### 敏感数据与密钥
- 代码/配置/日志里有没有硬编码密钥、token、连接串
- 日志、错误响应里有没有泄漏密码、完整身份证/手机号、堆栈细节
- 传输是否强制 HTTPS；敏感字段是否脱敏存储

### SSRF / 路径穿越
- 用用户提供的 URL 去发请求？→ 校验协议与目标，禁内网地址段
- 用用户提供的路径去读写文件？→ 规范化后校验是否逃出允许目录（`../`）

### 反序列化 / 依赖
- 有没有反序列化不可信数据（pickle、`yaml.load`、Java 原生序列化）→ 用安全变体
- 依赖有没有已知 CVE（`pip-audit` / `npm audit`）

### 其它
- 文件上传：类型、大小、存储位置、可执行性
- CORS 是否过宽（`*` + 携带凭据）
- 速率限制：登录、发码、重置密码等接口有没有防爆破

## 产出格式

发现按**严重度排序**（Critical → High → Medium → Low），每条包含：

```
[严重度] 标题
位置:   file:line
问题:   一句话说清是什么漏洞
利用:   具体输入/条件 → 造成的后果（说明可行性，不给即用攻击件）
修复:   具体怎么改（给出正确写法）
```

只报**能说清触发路径**的问题。说不清「什么输入→什么后果」的，标为「待确认」而不是混进确凿清单，避免虚报。

## 与其它技能配合

- 定位数据流不清楚时，先用 `feature-mapping` 把链路理出来
- 确认是逻辑 bug 而非安全问题 → 转 `systematic-debugging`
- 这是人工规则审查，深度多 agent 审查用 `/code-review`

## 反面案例

| 不要这样 | 要这样 |
|---|---|
| 「看起来还行」笼统结论 | 逐类清单排查，定位到 file:line |
| 报一堆「可能有风险」凑数 | 只报能说清触发路径的，其余标待确认 |
| 相信前端已经校验过 | 后端独立校验输入与权限 |
| 只看单点 | 跟着不可信数据走完整条路径 |
| 顺手写个 exploit 演示 | 说明可行性即可，不产出即用攻击件 |
