# Agent 记忆管理

## 何时使用本技能

- 用户明确说「记住 / 以后都这样 / 别再这样」
- 你发现了一个**跨会话有用、且无法从仓库重新推导**的事实
- 需要在新会话开始时召回并判断旧记忆是否还可信

## 核心判断：这条信息该不该进长期记忆？

只有**同时**满足两条才存：

1. **跨会话有用**——下次会话还会用到，不是只对当前任务有意义
2. **无法重新推导**——代码、git 历史、README、注释里都查不到

反例（不要存）：代码结构、某次 bug 怎么修的、文件在哪——这些代码本身就是答案，存了反而会过期骗人。

被要求记一件「代码里已有」的事时，追问一句「这里面**非显而易见**的点是什么」，存那个点，而不是存事实本身。

## 四种记忆类型

| 类型 | 存什么 | 例子 |
|---|---|---|
| `user` | 用户是谁：角色、专长、稳定偏好 | 「用户是安全研究员，偏好 Python」 |
| `feedback` | 工作方式的指导：纠正或确认过的做法 + 原因 | 「提交前必须先跑校验——上次漏了导致 CI 挂」 |
| `project` | 无法从代码得知的项目背景、目标、约束 | 「这个服务下季度要迁到 gRPC，新接口别再加 REST」 |
| `reference` | 外部资源指针 | 「监控面板 <url>、工单系统 <url>」 |

`feedback` 和 `project` 一定要带**为什么**和**怎么应用**，否则未来的你不知道该不该照做。

## 写入格式

一条记忆一个文件，带 frontmatter：

```markdown
---
name: <短横线-slug>
description: <一句话，用于召回时判断是否相关>
type: user | feedback | project | reference
created: <绝对日期，把「上周/下季度」换算成具体日期>
---

<事实本身。feedback/project 追加：>
**为什么：** ...
**怎么应用：** ...

相关：[[其它记忆的-slug]]
```

要点：

- **描述要能被检索**——召回时是靠 description 判断相关性的，写清适用场景
- **相对时间换成绝对时间**——「下个月」半年后就是错的
- **用 `[[slug]]` 互链**——把相关记忆连起来，哪怕目标还没写

## 去重与纠错

写之前先查有没有已存的同主题记忆：

- 已有 → **更新那一条**，不要新建重复的
- 发现旧记忆已经错了 → **删掉或改正**，过期记忆比没有记忆更危险
- 一件事实变了（偏好变了、项目方向改了）→ 覆盖旧值并更新日期

## 召回时的可信度判断

召回的记忆反映的是**写入当时**的情况，不是当下的事实。用之前：

- 记忆里点名了某个文件 / 函数 / 配置 → **先验证它还在**，再据此建议
- 记忆与当前代码矛盾 → 以代码为准，并考虑更新记忆
- 记忆越旧、越具体（指向具体代码位置），越要复核

## 维护索引

若记忆系统有索引文件（如 `MEMORY.md`），每写一条就加一行指针（标题 + 一句话钩子），保持索引与文件同步。索引只放指针，不放正文。

## 反面案例

| 不要这样 | 要这样 |
|---|---|
| 把「登录逻辑在 auth.py」存进记忆 | 不存——代码里就有 |
| feedback 只写「要小心」 | 写清做法 + 为什么 + 怎么应用 |
| 「下周上线」原样存 | 换算成绝对日期存 |
| 同一偏好存三个文件 | 更新已有那一条 |
| 召回后直接照记忆改代码 | 先验证记忆里的文件/函数还在 |
| 记忆过期了留着 | 删掉或改正 |
