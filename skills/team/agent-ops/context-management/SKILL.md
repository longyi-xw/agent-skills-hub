# 上下文管理

## 何时使用本技能

- 处理超长文件、超大仓库、超长对话
- 检索结果太多、信息开始互相淹没
- 感觉「前面说过的记不清了」「上下文快满了」
- 一个大任务要拆着做、或要交接给另一个会话/子 agent

## 核心原则：上下文是稀缺预算，不是垃圾桶

每放进上下文的一段内容，都在挤占对关键信息的注意力。默认**少放**，需要时再取。

```
决策顺序：能不能不放？ → 能不能放摘要？ → 能不能按需再取？ → 才考虑全放
```

## 三种手法

### 1. 分层加载（progressive disclosure）

不要一次读全部，按需下钻：

- 先读**目录结构 / 大纲 / 索引**，建立地图
- 再读**与当前子任务相关的那部分**
- 引用材料（长规范、大文档）放在外部，用时才读对应章节，读完可「忘掉」

技能系统本身就是这个思路：SKILL.md 只放触发条件和主流程，细节放 `references/` 按需加载。写自己的产出也照此分层。

### 2. 外置中间结果

长任务的中间产物写到**文件**，而不是全留在对话里：

- 检索到的清单、分析笔记、待办、进度 → 落盘到 scratchpad
- 需要时读回来，用完从上下文里放走
- 好处：对话被压缩/截断也不丢，还能交接

### 3. 子任务隔离

体量大、相对独立的活儿，丢给子 agent / 子会话去做，只把**结论**收回来：

- 「在整个仓库里找所有 X」这类大范围扫描 → 交给搜索型子 agent，拿回结论而非全部文件内容
- 主线程只保留决策所需的精炼结果，把翻找过程的噪音隔离在外

（并行拆分见 `dispatching-parallel-agents`。）

## 检索的纪律

检索不是搜得越多越好：

- 先用**窄查询**精确命中，不行再放宽，而不是一上来大海捞针
- 命中后只**读相关片段**，不整文件吞进来
- 同一信息不重复检索——记住已知结论，别反复查已经确认过的事

## 长对话的自我维护

- 定期在心里（或用简短小结）确认「当前目标、已完成、下一步」这三件事仍清晰
- 已经确定的决策不重新论证、不反复罗列备选
- 发现自己在重复读同一个文件 / 重推同一个结论 → 说明该把它外置成笔记了

## 交接 / 收尾前固化状态

当任务可能跨会话、要交给别人，或上下文即将被压缩时，先把状态固化成一段可独立读懂的交接说明：

```
## 目标
<一句话>

## 已完成
- ...

## 当前状态 / 关键结论
- <后续必须知道的事实与决策，附 file:line>

## 下一步
1. ...

## 坑 / 注意
- ...
```

写到文件里。这样即便上下文清空，新会话读这一段就能接上。

## 反面案例

| 不要这样 | 要这样 |
|---|---|
| 把整个大文件读进来再找 | 先看结构，只读相关段 |
| 检索结果几十条全留在对话里 | 落盘成清单，用时再取 |
| 大范围扫描亲自逐个翻 | 交给子 agent，收回结论 |
| 反复重读同一文件确认 | 记住结论或外置成笔记 |
| 上下文要满了才慌 | 提前把中间结果外置 |
| 交接时甩一句「你看聊天记录」 | 写一段自包含的交接说明 |
